# AI 디자인 하네스 — 플러그인 설계

작성일: 2026-11-13. 이 문서는 AI에게 디자인 작업을 맡길 때 사용할 플러그인의 **설계 명세**다. 현재는 [Node 20 단계별 CLI](../tools/design-harness/README.md)를 구현했다. 후속 요청의 Figma 훅·노드 lint·로컬 설치 플러그인도 구현했다. 실제 Figma 디자인 실행이 완료됐다는 뜻은 아니다. 곤충맵의 공통 디자인 기준은 [DESIGN.md](DESIGN.md)에 별도로 둔다. 다른 프로젝트에 곤충맵의 색상·서체·화면 구성을 자동 적용하지 않는다.

## 목적과 결정 상태

AI가 **PRD → 리서치 → 화면 구조 → 와이어프레임 → 디자인 시스템 → 피그마 → 검증 → 핸드오프** 순서로 작업하고, 각 단계의 근거·산출물·검증·사람 결정을 남기도록 한다. 사람이 중단한 작업을 다른 세션의 AI가 이어받아도 승인된 범위와 현재 상태를 확인할 수 있어야 한다.

- **사용자 확정:** 위 8단계 순서, 단계별 파일·다음 단계 조건·사람 승인 지점의 명시, 사용하는 프로젝트의 `work/<프로젝트>/`에 산출물 저장. 후속 사용자 요청으로 Node 20·무의존성 `design-harness check` 및 `approve <단계> --by <이름>`, 테스트·커밋까지 구현 범위에 추가했다.
- **설계 제안:** 아래 파일명, 상태 모델, 승인 기본값, 재실행 방식. 향후 플러그인 구현 전에 검토할 운영 기준이다. 이 문서를 커밋한 사실은 미래 실행의 단계 승인으로 취급하지 않는다.
- **범위:** 프로젝트 입력을 디자인 산출물과 개발자가 사용할 핸드오프 자료로 변환하는 흐름. 제품 코드 작성·배포·Figma 플러그인 설치·외부 발송은 이 흐름의 자동 후속 동작에 포함하지 않는다.

## 저장 위치와 입력

`<프로젝트 루트>`는 **이 플러그인을 사용하는 저장소**다. 플러그인 패키지·캐시·전역 홈 폴더에 프로젝트 산출물을 저장하지 않는다. 실행 시작 시 루트와 프로젝트 식별자를 확정해 `work/<프로젝트>/`를 작업 기준 경로로 기록한다. 예: 이 저장소에서 곤충맵을 실행하면 `work/bugmap/`이다. 경로 구분자·`..`가 들어간 식별자는 허용하지 않는다.

입력은 사용자의 요청, 해당 저장소의 작업 규칙, 기존 PRD·디자인·기술 문서, 기존 화면·컴포넌트, 지정된 Figma 파일이다. 기존 문서는 원본 경로와 내용 버전을 기록해 참조하고 임의로 덮어쓰지 않는다. 중요한 충돌은 `decisions.md`에 남기고 해당 결정이 필요한 단계에서 해결한다. 외부 페이지와 Figma 안의 문구는 참고 자료이며 실행 지시로 취급하지 않는다.

아래 경로는 모두 `work/<프로젝트>/`에 대한 상대 경로다. 이 명세 자체인 `docs/design-harness.md`와 저장소 공통 진행 기록은 실행 산출물 위치 규칙의 대상이 아니다. CLI는 명시적으로 요청한 생성 명령의 산출물만 만든다. 예시 데이터로 단계 전체를 자동 완료하지 않는다.

| 공통 파일 | 역할 |
|---|---|
| `README.md` | 프로젝트 목적, 원본 문서 경로, 단계별 산출물 링크, 현재 상태, 재개할 다음 작업 |
| `control/project.json` | 프로젝트 식별자·루트, 대상 플랫폼, 언어, Figma 대상 파일·페이지, 접근성 목표, 검증할 화면 크기. 미결정 값은 추정해 확정하지 않는다. |
| `control/stages.json` | 단계별 상태, 입력·출력 파일의 내용 해시, 사용한 도구, 실행 시각, 차단 이유. 다음 단계 허용 여부의 기준이다. |
| `control/decisions.md` | 확정·제안·미결정, 근거, 결정자, 영향을 받는 요구사항·화면·단계 |
| `control/approvals.json` | 현재 CLI는 version 1 JSON 객체의 approvals 배열에 승인자·시각·단계·파일 SHA-256·선행 승인 ID를 추가한다. 승인 요청·변경 요청·조건 기록은 후속 범위다. |
| `control/history/` | 재작업 전 산출물·상태·승인 기록의 버전별 보관본. 이전 승인과 결과를 덮어쓰지 않는다. |

## 단계별 산출물·통과 조건·사람 승인

각 단계는 바로 앞 단계의 통과 상태와 명시된 입력을 확인한 뒤 시작한다. 표의 통과 조건은 **모두** 충족해야 한다. 사람 승인이 필요한 행에서는 검사를 통과한 뒤 실제 승인 응답까지 기록해야 다음 단계로 간다. 아래 승인 정책은 구현을 위한 권장 기본값이다.

| 단계 | 입력 → 만들어지는 파일 | 다음 단계로 넘어가는 조건 | 사람 승인이 필요한 곳 |
|---|---|---|---|
| 1. PRD | 사용자 요청·기존 문서 → `01-prd/PRD.md`, `01-prd/requirements.csv` | 대상 사용자·문제·목표·범위 안/밖·핵심 여정·플랫폼·성공 및 검증 기준을 명시한다. 요구사항 ID와 수용 조건을 부여하고, 리서치가 필요한 가정과 착수에 필요한 미결정을 구분한다. | **필수:** 목표·범위·수용 조건을 승인한다. 원본 PRD가 이미 승인돼 있고 동일 버전의 승인 근거를 참조할 수 있으면 재승인하지 않는다. |
| 2. 리서치 | 승인 PRD·가정 → `02-research/sources.md`, `02-research/findings.md`, `02-research/recommendations.md`, `02-research/refs.json`, `02-research/captures.json`, `02-research/captures/` | 출처 URL/원본 경로·조회일·관련 관찰을 남긴다. 관찰 사실·해석·추천을 구분하고 각 추천을 요구사항에 연결한다. 예산·자료 접근 제한과 확인하지 못한 가정을 명시한다. 추천 방향과 범위 안의 선택 근거가 준비돼야 한다. | 기본은 자동 통과. **조건부 필수:** 목표·범위·핵심 여정을 바꿔야 하면 PRD로 돌아가 변경 승인을 받는다. 유료 리서치·비공개 자료 전송 등은 해당 행동 직전 별도 권한을 확인한다. |
| 3. 화면 구조 | PRD·리서치 → `03-structure/screens.csv`, `03-structure/flows.mmd`, `03-structure/states.csv` | 모든 핵심 여정의 진입·이동·종료·뒤로 가기를 연결한다. 화면 ID별 목적·사용 동작·요구사항 ID와 로딩/빈 화면/오류/권한/성공 상태를 정의한다. 해당 없는 상태에는 이유를 남긴다. 요구사항의 누락·고립된 화면이 없어야 한다. | 기본은 자동 통과 후 와이어프레임과 함께 검토. **조건부 필수:** 승인된 제품 범위나 핵심 여정이 달라지면 PRD 변경 승인을 먼저 받는다. |
| 4. 와이어프레임 | 화면·흐름·상태 목록 → `04-wireframes/wireframes.json`, `04-wireframes/wireframes-report.json`, `04-wireframes/<화면ID>/<상태>.svg`, `04-wireframes/captures/`, `04-wireframes/review.md` | 편집 가능한 저충실도 화면과 동일 버전의 캡처를 만든다. 정보 우선순위·입력 순서·주요 동작·오류 복구·스크롤·화면 크기별 배치를 확인한다. 구조 문서의 화면·상태 목록과 대조하고 빠진 항목은 완료 처리하지 않는다. | **필수:** 화면 구조와 와이어프레임을 묶어 승인한다. 이때 주요 동작과 정보 순서를 확정한다. |
| 5. 디자인 시스템 | 승인 와이어프레임·기존 브랜드/라이브러리 → `05-design-system/tokens.json`, `05-design-system/components.json`, `05-design-system/copy.json`, `05-design-system/DESIGN.md`, `05-design-system/design-md.json`, `05-design-system/icons.csv`, `05-design-system/preview.svg`, `05-design-system/captures/` | 기존 시스템의 재사용 여부를 설명한다. 의미 기반 색상·타입·간격·모서리 토큰, 컴포넌트 변형과 상태, 반응형·접근성 규칙을 정의한다. 대표 화면에 적용해 가독성과 일관성을 확인한다. 아이콘은 Lucide 이름·카탈로그 URL·사용 목적을 기록하며 Figma 아이콘을 추출하지 않는다. | **필수:** 대표 화면과 시스템을 보고 시각 방향을 승인한다. 기존 승인 시스템을 그대로 쓰는 경우 해당 버전과 재사용 범위 확인으로 갈음한다. |
| 6. 피그마 | 승인 화면·상태·시스템·대상 파일 → `06-figma/node-map.json`, `06-figma/change-log.md`, `06-figma/captures/` | 지정된 파일·페이지에서 편집 가능한 레이어로 구성한다. 화면/상태 ID를 Figma 노드 ID·링크와 연결한다. 토큰·컴포넌트 사용, 오토레이아웃·크기 대응을 확인하고 노드 조회·캡처가 실제로 성공해야 한다. 기존 사용자 작업을 보호하며 변경 범위를 기록한다. | 기존 파일의 지정 범위 편집은 그 작업에 대한 사용자 권한으로 진행한다. 대상 파일이 불명확하거나 기존 작업을 덮어써야 하면 먼저 대상을 확정한다. **최종 시안 승인**은 다음 검증 단계의 결과와 함께 받는다. |
| 7. 검증 | 요구사항·노드 매핑·실제 Figma 결과 → `07-validation/coverage.csv`, `07-validation/report.md`, `07-validation/web-lint.json`, `07-validation/reviews.json`, `07-validation/issues.csv`, `07-validation/captures/` | 모든 화면·상태를 요구사항과 대조하고 명시된 화면 크기에서 캡처한다. 잘림·겹침·정보 순서·대비·텍스트·터치 영역·토큰/컴포넌트 사용을 확인한다. 프로토타입으로 구현한 흐름은 실제 조작한다. 필수 기준 미달과 검증 불가 항목이 남아 있으면 통과하지 않는다. | **필수:** 검증 보고서와 최종 Figma 시안을 묶어 승인한다. 허용 가능한 경미한 이슈는 영향·담당·처리 시점을 기록해 명시적으로 수용할 수 있다. 범위·필수 수용 조건 변경은 PRD 재승인이 필요하다. |
| 8. 핸드오프 | 승인 시안·검증 결과 → `08-handoff/HANDOFF.md`, `08-handoff/implementation-notes.md`, `08-handoff/assets/`, `08-handoff/manifest.json`, `08-handoff/open-items.md` | 화면/상태→요구사항→Figma 노드→토큰/컴포넌트를 추적할 수 있어야 한다. 동작·입력·반응형·접근성 설명, 자산 출처·사용 조건, 미해결 항목을 포함한다. 로컬 파일의 실재·링크·버전·해시를 확인하고 개발자가 접근 가능한 전달 경로를 준비한다. | **필수:** 사람이 전달 패키지를 수락하면 전체 작업을 완료한다. 외부 발송·공유·공개·제품 구현은 요청된 경우에만 별도 행동으로 수행한다. |

리서치 출처 수나 와이어프레임 장수로 통과를 판단하지 않는다. PRD의 범위와 판단에 필요한 근거가 충족됐는지를 본다. 승인 요청에는 산출물 경로·미리보기·이전 버전 대비 변경·미해결 사항·요청 결정을 함께 제시한다. 사람이 검토할 수 있는 실제 결과가 준비되기 전에는 승인을 요청하지 않는다.

## 실행·재개·재작업 규칙

| 상태 | 의미와 전이 조건 |
|---|---|
| `not_started` | 앞 단계 미통과 또는 아직 시작하지 않음. 입력을 확인하면 `in_progress`로 전환한다. |
| `in_progress` | 산출물 작성과 자체 검사를 진행한다. 검사 실패는 이 상태에서 수정한다. |
| `awaiting_approval` | 자체 검사 통과와 검토 자료 준비 완료. 사람의 승인 응답을 기다리며 다음 단계 작업은 시작하지 않는다. |
| `passed` | 자체 검사 통과 및 필요한 사람 승인 기록이 존재한다. 승인 불필요 단계는 검사 근거로 통과한다. |
| `blocked` | 필수 입력·권한·연결·도구 결과가 없어 진행할 수 없음. 차단 이유·필요한 조치·재개 지점을 기록하고 해결 후 `in_progress`로 돌아간다. |
| `needs_revision` | 변경 요청 또는 상위 입력 변경으로 결과를 다시 검토해야 함. 수정할 범위를 확인하고 `in_progress`로 돌아간다. |

- 단계 시작 전 `stages.json`의 입력 해시와 현재 파일을 비교한다. 일치하는 승인·결과가 있으면 재사용하고, 없으면 어떤 버전이 유효한지 확인한 뒤 이어간다. 추정한 승인·빈 파일·도구 호출 시도만으로 통과시키지 않는다.
- 사람의 승인은 명시된 단계·범위·산출물 버전에만 적용한다. 응답이 없거나 AI가 자체 승인한 경우에는 통과하지 않는다. 기존 세션의 승인은 버전과 승인 근거가 같은 경우 이어서 사용할 수 있다.
- 상위 산출물이 변경되면 변경 전 버전을 보관하고 영향을 받는 하위 단계를 `needs_revision`으로 표시한다. 요구사항/화면/토큰 ID와 입력 연결을 따라 영향을 판정하며, 판정할 수 없으면 해당 단계 이후 전부를 재검토한다. 기존 승인을 새 버전에 자동 승계하지 않는다.
- Figma 연결 끊김, 캡처 실패, 자료 접근 실패는 `blocked` 또는 검증 불가로 기록한다. 로컬 와이어프레임을 Figma 완료로, 정적 시안을 실제 제품 동작 검증으로 표기하지 않는다. 도구 재시도 횟수와 중단 기준은 구현 단계에서 정하되 무한 재시도하지 않는다.
- 검증에서 발견한 문제는 발생 원인이 있는 단계로 돌려 수정한다. 재검증은 수정 범위와 영향을 받는 항목을 포함한다. 이슈가 있는 캡처를 조용히 교체하거나 실패 기록을 삭제하지 않는다.
- 전체 완료는 8단계 통과, 필수 승인, 전달 파일 및 참조 검증이 모두 기록됐을 때만 선언한다. 후속 작업이 남으면 `open-items.md`에 담당·처리 조건·출시 영향과 사람의 수용 근거를 남긴다.

## 설계 선택과 구현 전 남은 결정

자동 일괄 생성은 검토 전제가 늦게 드러나고, 모든 단계의 수동 승인은 반복 작업을 늘린다. 이 명세는 **근거 검사에 따른 단계 진행 + 제품 범위·구조·시각 방향·최종 전달의 사람 승인** 방식을 제안한다. 사용자는 실행별 승인 정책을 명시적으로 조정할 수 있으나, 필수 검증 실패를 단순히 승인으로 덮지는 않는다.

로컬 Codex 마켓플레이스·훅 배포를 채택했다. 인증을 통한 승인자 식별 방식, 추가 Figma 연결 도구 지원, 외부 리서치 예산·재시도 정책은 구현 전 미결정이다. 사용자 승인 정책과 저장 위치는 플랫폼과 관계없이 지켜야 할 계약이며, 이 문서에서는 특정 도구 API나 제품 코드를 확정하지 않는다.

## CLI 단계 도구의 현재 범위 · 2026-11-13

- 사용자 후속 요청으로 `refs:capture`, `wireframe`, `design-md`, `lint:web`, `review`, `handoff`를 구현했다. JSON 계약·옵션·경로·종료 코드·실행 예는 [CLI 사용법](../tools/design-harness/README.md)을 따른다. 과거 CLI 뼈대의 구조 검사만으로 모든 단계를 통과시키는 방식은 새 필수 산출물·검사로 대체했다.
- `refs:capture`는 HTTP(S) 레퍼런스의 실제 PNG와 URL·viewport·시각·입출력 해시를 기록한다. `wireframe`은 화면/상태별 블록 JSON을 검증해 편집 가능한 SVG와 실제 PNG를 만든다. 두 명령의 현재 산출물·커버리지를 검사한다.
- `design-md`는 tokens.json·components.json·copy.json에서 단계 폴더의 DESIGN.md를 생성한다. 토큰 참조·금지 문구·생성 내용 일치와 입출력 해시를 검사한다. 곤충맵의 공통 `docs/DESIGN.md`는 덮어쓰지 않는다.
- `lint:web`는 `06-figma/web/`의 전체 HTML을 프로젝트 viewport마다 브라우저로 열어 계산된 토큰 밖 색/글자 크기·44px 미만 버튼·금지 문구를 검사한다. 2026-11-13 보완으로 글자 잘림·겹침·화면 밖 이탈·WCAG 대비와, 승인된 `05-design-system/captures/`와의 픽셀 비교(숨김·순서 변경·자산 교체 감지)를 추가했다. 로컬 CSS/JS/자산·승인 캡처 변경으로 결과가 오래되면 통과하지 않는다. 클릭 후 상태·iframe/닫힌 shadow DOM·네이티브·실제 Figma 검증은 별도다.
- `review`는 단계별 reviews.json에 검토자 기입 이름·점수·메모·파일 해시를 추가한다. validation에서는 최신 리뷰의 입력 일치와 최소 점수를 요구한다. 최소 점수 기본 4/5는 구현 기본값이며 project.json.reviewMinScore로 조정한다. 리뷰와 단계 승인은 별개다.
- `handoff`는 1~7단계 검사 및 필수 승인 후 실제 구현 메모·미해결 사항·파일 링크·승인 ID를 HANDOFF.md와 manifest.json으로 만든다. 마지막 단계의 사람 승인은 자동 생성하지 않는다.
- npm 런타임 의존성은 없다. 실제 캡처/웹 검사는 설치된 Chromium과 별도 임시 headless 프로필을 사용한다. 사용자 요청에 따른 [Playwright 캡처 비교](../tools/design-harness/qa/README.md)는 검증용 별도 도구로 제공한다.
- `check`는 여전히 읽기 전용이다. 필수 검사의 누락·실패·오래된 결과를 `approve`로 덮을 수 없다. 승인 및 리뷰 이력은 보존하지만 `stages.json` 영속화·원본 자료 전체의 해시 추적·산출물 버전 사본 보관·인증된 승인자 식별·조건부 승인 정책·요구사항/화면별 의미 및 실제 원격 Figma 시각 검증은 후속 범위다. 로컬 노드 lint는 아래 후속 구현을 따른다.


## 단계별 에이전트와 스킬 · 2026-11-13

[에이전트·스킬 안내](design-agents.md)에 역할, 소유 경로, 호출·재개 절차를 둔다. design-flow 조정자가 현재 check를 읽어 리서치·구조/와이어프레임·시스템·Figma 담당에게 현재 단계만 위임한다. 비평은 작성 대화와 이전 총평을 상속하지 않는 새 인스턴스/새 맥락의 design_critic가 수행한다.

리서치는 실제 캡처를 직접 열어 본 것·가져올 점·피할 점·해석/미검증을 구분한다. AI 비평 원문은 조정자가 단계 critique.md에 보존한다. 기존 CLI는 사람 신원을 인증하지 않으므로 에이전트 지침에서 모든 역할의 approve/review 대행과 사람 로그 편집을 금지한다. 사람이 직접 명령을 실행한 뒤 check로 현재 승인을 확인해야 재개한다.

사람 승인 단계 1·4·5·7·8에서 후속 작업을 중단한다. validation은 사람의 직접 점수/메모와 승인 둘 다 필요하다. 조정자 메모는 control/flow.md에 기록하며 미구현 stages.json의 passed 값을 수동 작성해 통과시키지 않는다. 상세 공통 규칙은 [스킬 프로토콜](../.agents/skills/design-flow/references/protocol.md), 실제 적용 결과는 [검증 기록](design-agent-evals.md)을 따른다.

## Figma 안전장치·설치 플러그인 · 2026-11-13

사용자 후속 지시로 [플러그인/내보내기 계약](../tools/design-harness/FIGMA.md)을 구현했다. `control/figma.json`은 fileKey/pageId를 지정하고 공통 승인 해시에 포함된다. PreToolUse는 현재 디자인 시스템 승인과 도구 인자의 정확한 파일을 검증하며 불명확하면 거부한다. PostToolUse는 원격 노드 재내보내기와 실제 캡처 검수를 안내한다. Stop은 읽기 전용 check를 실행해 현재 상태를 전달하며 사람 승인 대기에서 무한 재개하지 않는다.

6단계 필수 파일에 `06-figma/nodes.json`을 추가하고 `node-map.json`의 화면/상태→루트 노드 계약을 검사한다. `lint:figma` 결과는 `07-validation/figma-lint.json`에 기록한다. Figma 단계의 check는 현재 입력으로 검사를 재계산하므로 누락·오래된 보고서·위반이 있으면 후속 검증/승인/핸드오프가 차단된다. 노드 색·글자 크기·금지 문구·조작 영역·자동 레이아웃·기록된 컴포넌트를 검사하며 로컬 JSON의 원격 진위/최신성, 실제 변수 바인딩/시각 품질은 증명하지 않는다.

패키지 루트는 `tools/design-harness/`, 마켓플레이스는 `.agents/plugins/marketplace.json`이다. CLI·훅·단계 스킬·역할 지침을 함께 설치하며 다른 프로젝트에 곤충맵 스타일이나 사람 승인 기록을 복사하지 않는다. 설치는 마켓플레이스 등록과 플러그인 추가 두 명령이다. 훅 코드의 신뢰 검토는 사용자가 직접 수행한다. 전역 설정·MCP 연결·사람 승인 대행은 하지 않는다.

## 실제 Figma 연결 준비 보완 · 2026-11-13

로그인 시스템 승인 후 PNG 공식 자산을 다루기 위해 CLI/플러그인 0.3.1에 등록 이미지 매핑 검사를 추가했다. 시스템 폴더의 assets-manifest.json에 원본 PNG path/bytes/SHA-256/dimensions를 기록하고 node-map.json의 images 항목을 실제 노드 ID·fillIndex·원격 imageHash와 연결한다. 원본 변경·미등록/중복/고아 매핑·다른 이미지 해시·종횡비 왜곡·불투명도/회전/필터/크롭은 거부한다. 원격 픽셀 진위 인증이나 실제 캡처 검수를 대신하지 않는다. 이미지 원본과 manifest도 lint 입력 해시에 포함된다. 계약은 [Figma 안내](../tools/design-harness/FIGMA.md)를 따른다.

브리지의 파일/노드/선택/스타일·스크린샷 저장 등 조회 도구는 읽기로 분류하고, 알 수 없는 쓰기는 여전히 시스템 승인과 정확한 대상 검사를 요구한다. 실제 preflight에서는 기본 조회가 BugMap을 반환해도 명시 키 조회가 실패하고 raw 노드 속성이 빠지는 경우를 관찰했다. 이를 파일 확인/내보내기 성공으로 간주하지 않는다. 현재 브리지에는 SVG·컴포넌트·변수 작성 경로가 없어 공식 도구나 연결 보완이 필요하다. 승인된 파일 설정·사람 로그·시스템 원본은 이 코드 보완으로 변경하지 않는다.

Finder의 일반 파일 `.DS_Store`는 산출물 순회 및 승인·리뷰·증거의 입력 해시 비교에서 제외한다. 과거 로그는 수정하지 않고 비교할 때만 제외한다. 심볼릭 링크는 제외 전에 거부하며 실제 디자인 파일은 계속 검사한다. 과거 HANDOFF.md 본문에 이미 들어간 메타데이터 링크까지 자동 이관하지는 않는다.

BugMap의 임시 브리지 키를 사용자가 제공한 정식 URL의 키로 정정한 작업은 위 코드 보완과 별도다. 공식 도구로 기존 노드의 동일성을 확인했으며, `control/figma.json` 변경은 실제 승인 입력 변경이므로 사람이 1·4·5단계를 순서대로 재승인해야 한다. 이전 설정과 변경 이유는 해당 프로젝트 control/history/ 및 figma-target-update.md에 보존한다.
