# BugMap 개발·배포 워크플로

제품 요구사항과 수용 기준은 [제품 PRD](PRD.md), 구현 설계는 [TDD](TDD.md), 승인된 디자인은 해당 화면의 인계서를 따른다. 에이전트는 [저장소 작업 규칙](../AGENTS.md)에서 이 절차를 시작한다.

## 기능 요청에서 사람 승인까지

**기능 요청 → Planning Agent → Coding Agent → Testing Agent → Review Agent → 사람 승인 → 배포**

| 담당 | 모델 | 다음 단계에 전달할 결과 |
| --- | --- | --- |
| Planning Agent | 세션의 기본 모델 | 요구사항, 수용 기준, 범위, 미결정 사항, 관련 Figma·문서, 검증 절차를 정리한다. 계획을 수정하는 파일이 있으면 별도로 커밋한다. |
| Coding Agent | GPT-6.2 Sol (`gpt-6.2-sol`) | 계획을 기준으로 구현하고 필요한 로컬 검사를 실행한다. 브랜치, 구현 커밋 SHA, 변경 요약과 검사 결과를 전달한다. |
| Testing Agent | GPT-6.2 Astra (`gpt-6.2-astra`) | 구현 커밋을 독립된 작업 환경에서 체크아웃하고 수용 기준·회귀를 검증한다. 실행 명령, 환경, 성공·실패·미실행 여부를 SHA와 함께 남긴다. 회귀 테스트를 추가한 경우 별도 커밋으로 전달한다. |
| Review Agent | 세션의 기본 모델 | 최종 후보의 diff와 검사 증거를 검토해 정확성, 보안, 범위, 회귀 위험을 보고한다. 발견 사항은 PR에 남기고 필요한 수정을 Coding Agent로 돌려보낸다. |
| 승인자 | 사람 | 리뷰와 필수 검사 결과가 현재 후보에 해당하는지 확인하고 병합·배포를 승인한다. |

사용 가능한 모델은 실행 환경에서 확인한다. Sol 또는 Astra를 선택할 수 없으면 제한을 알리고 실제 사용 모델을 기록한다. 구현이 바뀌면 새 후보 SHA 기준으로 영향을 받는 테스트와 리뷰를 반복한다. 변경 요약과 함께 담당 역할, 모델, 기준 SHA, 결과 SHA, 검증 증거, 남은 일을 전달한다.

## 역할별 브랜치와 커밋

에이전트마다 브랜치와 Git worktree를 쓸 수 있다. 작업별 통합 브랜치를 두고, 수정이 있는 담당은 직전 산출물의 SHA에서 역할 브랜치를 시작한다. 작은 변경은 통합 브랜치 하나에서 역할별 커밋으로 이어갈 수 있다. 테스트와 리뷰가 조회 중심이면 검증 SHA와 결과를 PR에 기록한다.

| 브랜치 예시 | 시작점 | 통합 방법 |
| --- | --- | --- |
| `feat/first-login` | 작업 시작 시점의 기준 브랜치 | 최종 PR을 열고 검증할 후보 SHA를 정한다. |
| `feat/first-login-plan` | 통합 브랜치의 시작 SHA | 계획 파일 변경을 통합한다. |
| `feat/first-login-code` | 계획 통합 후 SHA | 구현 커밋을 통합한다. |
| `feat/first-login-test` | 구현 통합 후 SHA | 독립 검증 결과를 남긴다. 테스트 파일을 수정한 경우 테스트 커밋을 통합한다. |
| `feat/first-login-review` | 테스트 반영 후 최종 후보 SHA | 격리 검토가 필요할 때 사용한다. 결과는 최종 후보 PR에 남긴다. |

통합할 때 선형 인계가 가능하면 fast-forward를 사용한다. 검토 이후 후보가 변경되면 기존 결과를 그대로 재사용하기 전에 새 SHA에서 필요한 검사를 다시 실행한다. 역할별 커밋이 대상 브랜치에도 남아야 하는 작업은 PR 병합 방식을 정할 때 커밋 보존 여부를 확인한다.

## 코드 푸시부터 배포까지

**코드 Push → 자동 빌드 → 테스트 → 보안 검사 → 사람 승인 → 배포**

1. 기능 브랜치를 Push하고 PR을 연다. CI는 Push와 PR 갱신 시 후보 커밋의 자동 빌드를 시작한다.
2. 빌드가 성공하면 타입 검사, 자동 테스트, 변경 기능의 수용·회귀 테스트를 실행한다. 현재 저장소의 기본 명령은 `npm run export:web`, `npm run typecheck`, `npm test`다. `npm test`는 디자인 하네스를 검사한다. 로그인·지도 변경의 수용 테스트는 별도 증거로 남긴다.
3. 의존성 취약점과 비밀값 노출 여부를 포함한 방어적 보안 검사 결과를 PR에 남긴다. 실패한 필수 검사는 수정 후 새 후보 커밋에서 다시 실행한다.
4. 에이전트 리뷰와 필수 검사가 끝나면 사람이 승인한다. 병합 또는 릴리스 과정에서 후보가 바뀌면 배포할 결과에 대응하는 검사와 승인 여부를 확인한다.
5. 승인된 커밋에서 만든 산출물을 배포하고 배포 환경·버전·결과를 기록한다. Expo 네이티브 릴리스는 웹 빌드와 별개로 대상 플랫폼의 빌드와 실기기 검증 결과를 확인한다.

이 절차의 CI 트리거, 필수 상태 검사, 승인 게이트와 배포 연결은 CI 및 저장소 설정에서 적용한다. 이 저장소에서 확인한 시점에는 CI 워크플로 파일이 없다.

## Figma 연결

기본 도구는 Figma 데스크톱의 Cursor MCP Plugin과 Cursor Talk to Figma MCP 브리지다. 현재 파일과 페이지에서 활성화된 채널에 연결하고, 파일명·페이지·대상 프레임을 대조한다. 브리지가 파일 키를 제공하면 함께 검증한다. 파일 키가 없는 연결은 사용자가 지정한 파일 링크와 데스크톱의 파일·페이지·대표 프레임으로 대조한다.

플러그인이 닫혔거나 재시작되어 연결이 끊기면 현재 채널을 확인한다. 작업에 필요한 명령이 지원되지 않으면 제약을 알리고 가능한 대안을 제시한다. 디자인 하네스의 승인과 실제 노드·캡처 검수는 [디자인 하네스](design-harness.md) 기준을 따른다.
